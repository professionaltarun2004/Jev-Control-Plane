## Run a mock plumbing experiment

The clone, virtual-environment, installation, and test steps are in the [README quick start](../README.md#quick-start-offline-mock-path). From the activated environment and repository root, run:

```sh
python examples/run_mock_experiment.py
```

No Jev API key is required for this command. It uses the deterministic mock adapter and reads only the Development dataset. The command prints a unique run ID and directory under `experiments/runs/`. Inspect `manifest.json` for the selected mode and reproducibility metadata, `summary.json` for aggregate plumbing metrics, and `results.jsonl` for per-case records and raw control-plane evidence. Preserve failed case rows; do not treat mock answers, latency, or throughput as Jev observations.

Run the offline test suite with:

```sh
python -m unittest discover -s tests -v
```

The tests use temporary fixtures for split and lock behavior. They do not access the repository's Holdout data or issue Jev API calls.

## Run the M4 paired mock plumbing check

After installing the project, run:

```sh
python examples/run_mock_comparison.py
```

This runs the existing deterministic Jev-shaped mock control path and a separate deterministic LLM-shaped action fixture over the same Development cases. Neither condition receives expected labels or annotation notes; the judge mock is not a language model. It makes no network calls and needs no credentials. Output is written to `experiments/comparisons/runs/<run-id>/`:

| File | Contents |
| --- | --- |
| `manifest.json` | Schema/config versions, condition identities, dataset/annotation digests, code metadata, and explicit mock-only limitations |
| `attempts.jsonl` | One label-free provider attempt per condition and case, including native output, status, latency, and Jev policy result where applicable |
| `pairs.jsonl` | Evaluator-owned expected outcomes and per-case action correctness after both attempts |
| `summary.json` | Paired counts, valid-pair denominators, and failure counts by condition |

The Jev side uses the existing legacy mock policy; the judge mock emits a direct action without that policy. Policy-level equivalence is therefore disabled. The paired counts are only plumbing checks on synthetic Development labels, not a fair model comparison or evidence about Jev/LLM quality. Recorded latency is local adapter overhead, not model inference latency. Validation and Holdout are rejected by this runner.

The Python CI workflow also runs this example and validates the generated manifest, summary, attempts, and pairs. It checks the actual Development case count, a complete two-condition attempt matrix, unique IDs, recognized statuses and action fields, label isolation in provider attempts, evaluator labels in pair records, and reconciliation between per-case outcomes and aggregate metrics. The manifest's `status` means the artifact set was finalized; `execution_status` separately reports whether every condition returned an action or whether any abstention, provider failure, malformed result, or runner error occurred. A fatal interruption before finalization leaves the manifest at `running`. The offline run requires no credentials or network access. Passing CI establishes serialization, pairing, and isolation plumbing only; it does not establish real-world decision quality or comparative model performance.

## Data layout

Each split keeps `cases.jsonl` and optional `annotations.jsonl` sidecars. Cases contain state, decision, and ground truth with provenance/certainty; annotations contain perturbation family, description, and optional matched `base_case_id`. See [dataset details](datasets/README.md) and the [ground-truth construction rules](datasets/ground_truth_rules.md).

## Experimental discipline

Development supports iteration. Validation supports protocol and policy selection. A LOCK freezes the Validation configuration, Validation run artifact digest, data/annotation digests, software/code identity, and prepared Holdout digests. A lock permits one Holdout attempt for that exact data snapshot; interrupted attempts remain claimed. This is an accidental-drift gate, not tamper-proof storage or a statistical guarantee. See the protocol for definitions and limitations.

Metrics distinguish evidence observations (agreement, disagreement, unmapped views, confidence/probabilities) from outcome categories (final-action, Jev-consensus, policy, or runner errors). A disagreement is not itself an outcome error. Accuracy is exact final-action agreement among completed decisions; runner errors are counted separately. Calibration, ECE, Brier score, risk-coverage, SAC, trajectory outcomes, and cost are not reported without a supporting design and data.

No charts are generated from the current small synthetic fixture. A visualization should be added only when machine-readable experiment results support an interpretable plot.

### Historical mock observations

The three preserved pre-M2.5 mock runs each contain 8 attempted/completed Development decisions, 5 exact-action matches, 3 mismatches, 8 policy escalations, and 0 runner errors. Thus the recorded mock accuracy is 62.5% and escalation rate is 100% in each run. Median local mock loop times were 0.207 ms, 0.221 ms, and 0.475 ms respectively; these are harness observations and not Jev latency or a meaningful throughput comparison. Each run has fewer than 20 observations, so its p95 was withheld. The summary labels and case-family analysis in these historical artifacts follow the old taxonomy, including disagreement-as-failure; the corrected M2.5 runner separates evidence from outcomes. These numbers characterize only the old deterministic fixture and must not be described as Jev findings.

The latest current-schema mock smoke run attempted 8 Development decisions: 5 matched ground truth, 3 did not, all 8 escalated, 0 runner errors; accuracy was 62.5%, escalation rate 100%, and evidence status was 1 agreement / 7 disagreements. Median local mock-loop time was 0.357 ms and p95 was withheld at n=8. Its matched irrelevant-context pair retained identical expected action; both outputs escalated and both missed the expected ALLOW. These deterministic mock runs validate artifact generation and analysis wiring only; they are not Jev observations or evidence of an irrelevant-context effect.
